## Highest-priority findings

### P1 — Ad-request eligibility is being converted into analytics and attribution consent

**Confirmed source defect.** iOS `Sources/OverLitIOSSupport/Services/Ads/AdMobAdService.swift:150-157` defines `consentGatheredForCurrentAudience` as `canRequestAds && !audienceInvalidatedSinceLastGathering`. `App/OverLit/OverLitKMPAppRuntime.swift:2431-2467` uses that answer plus legal/age gates to enable Firebase collection; `:2489-2508` uses the same answer to opt in Tenjin. Android `AndroidFirebaseAnalyticsPort.kt:184-193` and `AndroidAttributionPort.kt:218-225` use the equivalent three-input rule. The shared permitted posture explicitly grants `ANALYTICS_STORAGE` (`shared/application/.../state/MeasurementConsentPostureV1.kt:85-90`). iOS actually writes the grant at `OverLitAnalyticsReporting.swift:409-410`.

Google's ability to request a permitted ad is not a purpose/vendor consent grant for product analytics or a different attribution recipient. Refusal can still allow limited/contextual ads. Google's own [GDPR integration guidance](https://developers.google.com/admob/ios/privacy/gdpr) distinguishes purpose and vendor choices from a single bit; its [app Consent Mode guide](https://developers.google.com/tag-platform/security/guides/app-consent) requires updating consent values from user choices and honoring revocation. Source comments admitting that UMP's TCF answer has no analytics purpose, then arguing that restoring `analytics_storage` is merely reversing a previous app denial, do not supply a user choice.

**Public contradiction:** Website `overlit-privacy-policy.md:412-426` says the form carries `analytics_storage`, governs analytics, and refusal stops the attribution partner. Those promises are not implemented by the boolean above. This affects fresh refusal, partial consent, and withdrawal where `canRequestAds` stays true. iOS's dismissal refresh at runtime `:2759-2770` still re-reads the wrong fact.

**Correction:** Introduce independently evidenced purpose/recipient permissions for analytics storage, attribution processing, ad user data, and personalization. Keep ad eligibility separate. Use a CMP actually configured to cover those purposes and recipients, or a clear first-party optional analytics/attribution control; do not assume UMP automatically supplies an analytics choice. Unknown/missing signals must withhold optional measurement. Keep withdrawal available after purchase and where UMP has no privacy-options form. Reconcile notice with the real interface. Test reject-all with `canRequestAds=true`, partial/vendor denial, withdrawal, relaunch, and Full Version. [EDPB consent guidance](https://www.edpb.europa.eu/sites/default/files/files/file1/edpb_guidelines_202005_consent_en.pdf) is the legal basis for requiring a specific affirmative choice and an effective withdrawal path; this audit does not decide every country's applicable basis.

### P1 — Android hardcodes attribution ad consent and leaves privacy-form dismissal disconnected

**Two confirmed code paths.** `androidApp/src/main/java/com/overlit/android/services/AndroidAttributionPort.kt:122-135` calls `optIn()`, `setGoogleDMAParameters(true, true)`, `optInGoogleDMA()`, and `connect()`. Those true values are not read from the person's personalization/ad-user-data choices. Tenjin's [SDK documentation](https://tenjin.com/docs/mmp-sdk-ios/) explains that the setter overrides CMP-derived DMA choices. Android's fixed grants must be removed before enabling its currently unconfigured key.

Separately, `androidApp/.../MainActivity.kt:561-565` calls `service.presentPrivacyOptions()` without a callback. `AndroidUmpConsentService.kt:337-344` defaults that callback to an empty function and neither reports a new consent outcome nor refreshes the state store. `AndroidAdSdkState.kt:80-101,158-175` updates its cached boolean through other paths. Therefore dismissing the Settings form does not propagate the new choices immediately into app-owned analytics/attribution/readiness state. This remains a defect even after replacing the coarse consent boolean.

**Correction:** On dismissal, obtain a fresh complete consent snapshot, invalidate preloaded ads whose permission changed, update all measurement SDKs, and publish the new state before releasing further events. Drive DMA values from that snapshot. Test an initialized adult session, revoke purposes/vendor permission in Settings, then trigger an event without navigation/restart. Assert SDK calls and queued delivery stop immediately. Preserve error/failure as denied or last demonstrably valid permission, not an invented grant.

### P1 — ATT denial is described as aggregate-only, but iOS sends Tenjin device-associated events

**Confirmed disclosure gap; actual cross-company tracking needs vendor/dashboard/network verification.** The iOS attribution start predicate does not include ATT authorization (`OverLitKMPAppRuntime.swift:2431-2508`). `OverLitAttributionReporting.swift:213-260` starts/opts in/connects Tenjin, then `:285-300` sends milestone event names; its `adUserData` and `adPersonalization` arguments are unused. Importantly, `optInGoogleDMA()` is not itself the same thing as Android's explicit true/true override, so do not report both platforms as having an identical DMA implementation.

Tenjin's checked-in SDK README, `.build/checkouts/tenjin-ios-sdk/README.md:330-375`, says `developer_device_id` is required to process events and identifies it as IDFV. No app call restricts this to an Apple-only aggregate channel. Public policy `:228-242,424` omits IDFV and asserts that ATT refusal leaves aggregate measurement that cannot follow someone between companies' apps. Removing IDFA alone does not establish that claim. Apple's [privacy rules](https://developer.apple.com/app-store/user-privacy-and-data-use/) require ATT for tracking via other identifiers too and prohibit fingerprinting; third-party SDK behavior remains the developer's responsibility.

**Related concrete manifest defect:** `App/OverLit/PrivacyInfo.xcprivacy:30-53,76-83` explicitly records that Tenjin's manifest uses `https://track.tenjin.com` and deliberately does not add the bare domain because blocking denied-ATT traffic would change behavior. Inspection confirms the malformed entry in `.build/checkouts/tenjin-ios-sdk/TenjinSDK.xcframework/ios-arm64/TenjinSDK.framework/PrivacyInfo.xcprivacy:5-10`. Apple's [tracking-domain documentation](https://developer.apple.com/documentation/bundleresources/app-privacy-configuration/nsprivacytrackingdomains) explains that requests to declared tracking domains fail without permission. Omitting a known tracking domain is not a remedy for unwanted blocking.

**Correction:** Verify the exact configured Tenjin data fields, matching method and network postbacks for denied/restricted/not-determined ATT. Either withhold device-associated attribution until authorized or use a demonstrably non-tracking configuration with an accurately described IDFV/pseudonymous scope. Preserve Apple's aggregate attribution separately where lawful. Correct tracking domains with the matching behavior change and inspect the merged release manifest. Do not merely delete the policy's reassuring sentence while continuing unverified tracking. Add tests for ATT denied before startup and authorization revoked during a session.

### P1 — Crashlytics notice omits automatic gameplay breadcrumbs and non-crash session traffic

**Confirmed SDK/source discrepancy, runtime delivery subject to enabled collection/settings.** Website policy `:324-334,364` says crash reports contain nothing about play, are never combined with analytics, and that no session ping occurs or data leaves unless the app crashes. Both Analytics and Crashlytics are linked. The actual Firebase dependency registers an analytics listener at `.build/checkouts/firebase-ios-sdk/Crashlytics/Crashlytics/Controllers/FIRCLSAnalyticsManager.m:62-90`, serializes event names and parameters into crash logs, and emits `app_exception` into analytics (`:93-107`). Firebase explicitly documents [automatic analytics breadcrumbs, including custom-event parameters](https://firebase.google.com/docs/crashlytics/ios/customize-crash-reports). This can include the disclosed level/outcome/duration/star gameplay events when analytics is enabled.

Crashlytics also subscribes to Firebase Sessions (`.../Crashlytics/Crashlytics/FIRCrashlytics.m:168-177`). `.../FirebaseSessions/Sources/FirebaseSessions.swift:165-212` creates a session-start event and dispatches it when a subscriber permits collection and sampling/settings allow it; `SessionCoordinator.swift:70-77` adds installation ID/auth token. No crashing prerequisite exists. Thus a blanket no-session/no-non-crash-traffic claim is false for the inspected SDK stack. Google's [Firebase privacy inventory](https://firebase.google.com/support/privacy) also lists a Firebase session identifier and more diagnostics than the notice's two-ID description.

**Correction:** Document the SDK's automatic breadcrumbs, session/stability telemetry, identifiers, and conditions, or deliberately disable the unwanted integration using supported APIs/build configuration and verify traffic. Inspect an actual test crash and a crash-free cold launch on both platforms. Reassess the `Crash Data = not linked` worksheet entry (`Docs/store/app-store-connect-privacy-answers.md:32,67,80`) rather than assuming absence of a custom user ID makes data unlinked. Apple's [definition](https://developer.apple.com/app-store/app-privacy-details/) includes device linkage and third-party handling, not just names/accounts. This is a classification review, not an assertion that every diagnostic row must mechanically be marked linked.

### P1 — Crash collection can precede current legal acceptance; “disabled” does not erase old reports

**Confirmed startup mismatch and documented SDK behavior.** `OverLitApp.swift:89-94` configures Firebase before runtime state is resolved. `OverLitCrashReporting.swift:69-78` explicitly acknowledges that a persisted SDK true value outranks the default false and can upload before a returning user accepts new legal versions. Android's crash port documents the same window at `:63-69`. Policy `:330,428` promises collection only after accepting the current documents. Native calls only change the SDK flag; neither port deletes unsent reports.

The comments say disabling early would discard the previous report. That premise conflicts with Firebase's [opt-in reporting documentation](https://firebase.google.com/docs/crashlytics/ios/customize-crash-reports): disabled collection stores crash information locally, which can upload when enabled later. Consequently a teen's locally captured report may also become uploadable after changing to adult unless explicitly discarded. Do not assert this occurred to real users without a runtime reproduction.

**Correction:** Resolve permitted collection before auto-upload, or use an explicit unsent-report send/delete lifecycle; deliberately decide what to do with reports captured while ineligible. Verify the pinned SDK's semantics for toggles during a session, persisted overrides, legal-version updates and adult↔teen transitions. Keep reports withheld rather than assuming a default plist key always wins. Reword the policy only after that choice is implemented and measured.

## Other material findings

### P2 — Audience provenance is process-local; interrupted age changes can reuse a previous audience's consent

iOS `AdAudienceTransitionState.swift:14-21,45-62` retains invalidation only in memory. Android `AndroidUmpConsentService.kt:125,159,238` uses an in-memory atomic audience and seeds it to the current audience before a new update completes. `AndroidAdSdkState.kt:158-165` seeds raw persisted UMP eligibility. The application can persist a teen→adult choice and die before successful gathering; on restart the guard no longer proves the old UMP answer belongs to that adult. A failed update can then use cached eligibility. This is a strong source-derived edge case, not a completed device reproduction.

Persist a minimal consent-context receipt/invalidation epoch with the committed audience change, or require successful current-context gathering before optional measurement after every uncertain transition. Do not call Google's test-only `reset()` in production as the fix. Test kill-after-band-commit, relaunch offline, and failed update before any SDK enable call. Also test regional narrowing changes.

### P2 — The web deletion route depends on access to the app, and the app confuses progress with identity existence

Website `overlit-data-deletion.md:28-34` directs users to copy an ID from Settings and says requests cannot be actioned without it. This fails someone who already uninstalled without saving that ID. Google [explicitly requires the web route to work without reinstalling](https://support.google.com/googleplay/android-developer/answer/13327111?hl=en). Do not replace it with “nickname proves ownership”: names are intentionally non-unique.

Separately, `ApplicationSettingsPresentationV1.kt:1622-1625,1722-1749` enables deletion and ID-copy based on `leaderboardsAvailableV1(progress,...)`; `ApplicationLeaderboardEligibilityV1.kt:68-75` requires current progress unlock and online feature enablement. If an iOS anonymous credential survives reinstall while local Level 5 progress does not, the UI says no account exists and disables deletion even though a server identity does exist. A future feature-off build has the same problem. Turning off the user participation toggle is correctly bypassed; current progress is not. Apple [requires deletion for automatically created/guest accounts](https://developer.apple.com/support/offering-account-deletion-in-your-app/).

Base deletion/ID-export on whether a credential/identity exists (without creating one simply to delete), independently of feature/progression state. Provide an uninstall-safe recovery/deletion token or carefully verified support route that accepts a request without the installed app; describe honestly when the controller cannot identify records, with proportional verification. Delete-data copy also wrongly says only leaderboards hold server data (`:5-6`), omits Tenjin/Firebase handling, points to privacy section 14 instead of 15 (`:63`), and omits the policy's other-player-cache retention exception. Correct these now as accuracy fixes; do not invent a functioning recovery mechanism in prose.

### P2 — Server deletion has no durable barrier against concurrent writes

`firebase/functions/src/api/deleteIdentity.ts:52-65` sequentially removes entries, submissions, rating, player, then Auth. There is no deleting/deleted tombstone that every writer checks. `ensureNickname` can recreate a profile (`infra/playerProfile.ts:45-62`); `submitRun.ts:366-418` writes rows and ledger without a deletion state check. `api/shared.ts:53-59` accepts an authenticated request's UID; it does not check account existence/revocation. Therefore an already-authorized concurrent request can recreate data after the corresponding deletion stage. In-app serial barriers protect that client, not an overlapping backend request or another credential holder. Firebase [ID-token/session guidance](https://firebase.google.com/docs/auth/admin/manage-sessions) describes short-lived ID tokens and explicit revocation checking, so deleting the Auth user alone should not be treated as instantaneous invalidation of every in-flight authorized operation.

Add a durable, minimal deletion marker checked transactionally by every writer before mutation, drain/cancel in-flight work, revoke/delete Auth, and repeat cleanup safely. Expire the marker only after the necessary token/in-flight window; document that limited security retention. Add emulator concurrency tests, including getProfile/reroll/submit during deletion and replay with an old token. No live attack was attempted.

### P2 — Retention promises exceed what the configured source guarantees

Policy `:150,174,483,503` says ledger copies expire within 30 days. Backend writes `expireAt = now+30d` (`submitRun.ts:415`, `config/constants.ts:103`), but [Firestore TTL](https://firebase.google.com/docs/firestore/ttl) is asynchronous, typically deleting within 24 hours after expiry; it is not a strict at-30-days guarantee. The index manifest does not itself establish a deployed TTL policy. Verify production TTL enablement and monitoring; say scheduled to expire after 30 days and explain deletion delay, or implement a stronger erasure mechanism if that bound matters.

Policy `:489` says no copy survives deletion anywhere, contradicting its own other-player-ledger exception (`:503`) and retained logs. A 2026-09-03 source note about backups cannot establish today's configuration. Narrow to active identity-linked database records, state cached response/log/provider exceptions, and recheck PITR, backups, exports, log buckets and retention. `:487` says log periods are set by Google rather than configured by the developer; do not make that absolute statement without checking adjustable project/bucket settings. No default duration is certified here.

### P2 — Public output/data-location descriptions are incomplete

Policy `:159` says platform is not displayed and no timestamps are shown. Actual `firebase/functions/src/infra/boardReads.ts:461-465` returns `platform`; it also sends base64url JSON continuation cursors (`:49-59,105-106,157-164`) containing an entry's precise acceptance timestamp, score and cohort. A UI may hide a field while the client receives it. Disclose public/client-visible platform and pagination metadata, or move cursor state server-side/use an opaque token. This is not a UID leak: the inspected DTO/cursor deliberately excludes UID.

The policy's `:138` “exactly these fields and nothing else” must distinguish the business payload from Auth/App Check/IP/request metadata. It already discloses some of the latter elsewhere, but the absolute sentence is misleading.

The iOS bootstrap falls back from App Attest to DeviceCheck in production (`OverLitFirebaseBootstrap.swift:15-18`), whereas policy `:50,165,527` names only App Attest. Disclose the fallback. Attestation strengthens authenticity; avoid claiming it proves every installation is unmodified.

Policy `:379,394` describes Auth as a global Google service and broadly says leaderboard records stay in the EU. Firebase's [current privacy documentation](https://firebase.google.com/support/privacy) says Authentication runs exclusively in US data centers. Scope Belgium specifically to the configured Firestore database and function region; identify US Auth processing, global App Check/provider service metadata, and assess transfer safeguards on actual contracts/settings. Regional function code alone does not verify the database or every recipient's location.

### P2 — Read-only leaderboard use still creates personal-data records

`ApplicationLeaderboardEligibilityV1.kt:85-88` says viewing mints no identity and stores nothing about the viewer. Backend calls all require Auth (`api/shared.ts:53-59`); `getProfile.ts:58-64` consumes per-UID allowance and creates a nickname/profile; `getOverallBoard.ts:49-59` similarly does so. A view-only teen can therefore have an anonymous account/private server record even without score publication. The public policy partly explains anonymous auth on the first service contact, but the internal legal argument for exempting viewing is false and creates a dangerous future change premise.

Document that publication-off does not mean no server processing, and distinguish private view-related processing from public scores. Assess necessity/minimization and the children's legitimate-interest balance using the real flow. If anonymous public reading is desired, implement it deliberately with abuse controls rather than claiming it exists.

The broad power to stop or remove features (`terms:154`) and EUR25/12-month liability cap (`:182-187`) deserve a focused Polish/EU consumer review for the paid digital content offering; a generic “to extent permitted” saving clause should not be treated as proof all exclusions are enforceable. [EU digital-content legislation](https://eur-lex.europa.eu/eli/dir/2019/770/oj/eng) supplies the relevant conformity/remedies framework. Do not add an invented no-refund rule or a blanket waiver of withdrawal rights.

Release status remains unproven. Android source says `versionName=2.0.3`, `versionCode=5` (`androidApp/build.gradle.kts:237-245`), while `project.yml:11-12` says iOS `2.0.1`/`1`; a nearby Android comment incorrectly claims those match. Before release, record store build/version/commit, resolved release SDKs/manifests, effective UMP messages/vendor purposes, Firebase sharing/retention settings, Tenjin destinations/ATT behavior, app-store privacy declarations, and the deployed website commit. Keep source, release binary and dashboards as three separate evidence classes.

## Skill/workflow gaps that allowed the issues

1. **Consent truth is never tested.** The skill repeatedly checks “UMP ran / canRequestAds” and SDK call parity. Add mandatory tests where the form completes but all or selected purposes/vendors are denied; inspect actual SDK/network data rather than a passing boolean mock.
2. **Parity can preserve a privacy defect.** Matching platforms is useful but not an authority. Android's DMA hardcoded grant and iOS's unused parameters show why semantic assertions must accompany parity checks.
3. **No SDK-default inventory.** Require linked-SDK source/docs review for automatic events, IDs, breadcrumbs, session transport, crash caching, default/persisted collection and deletion. “The app never calls setUserID/log” is insufficient evidence of no linkage/content.
4. **Known manifest under-declaration is recorded as an owner decision instead of a release blocker.** A behavior-changing correction needs coordination, but leaving the tracker undeclared should not be presented as a compliant standing posture.
5. **Non-durable audience proof.** Add kill/relaunch, failed update, changed age/region, ATT revoke and purchased-user scenarios to consent testing; current in-process tests cannot prove these.
6. **Deletion checklist conflicts with actual product.** Website skill says email nickname works after uninstall, but policy requires an app-only ID and correctly notes nickname ambiguity. Require an executed uninstall-safe rights path plus credential/progress independence and backend concurrency tests.
7. **Version instructions contradict.** Website `skills/legal-update-sync/SKILL.md` says clarifications must not bump; its CHECKLIST step 3 says any legal edit bumps. App legal-sync cross-repo order still says patch bump for wording despite its earlier no-bump rule. `reenable-admob/references/admob-reenable-playbook.md` still tells editors to change `PlayableLegalDocumentCatalog.current.privacy.version`, which the current app skill forbids (the canonical strings are now in `LegalAgePolicyV1`). Correct these pointers/rules without triggering a user gate.
8. **Assertions are mistaken for evidence.** Several comments pronounce legal conclusions (“no identity when viewing”, “undoing a denial is not consent”, “disabling discards crash reports”) contrary to source or provider docs. Require primary-source verification and label owner choices, assumptions, and observed behavior separately. The skill's prohibition on silently reversing legal policy is sensible; it should not prevent reporting that the policy premise is wrong.
9. **Store answers should be reviewed from actual processing**, not copied from a vendor manifest or assumed to update automatically from the merged report. Add a build-stamped checklist linking the release privacy report and manually submitted App Store/Play answers.

## Recommended order

First correct the consent model and Android withdrawal callback. Resolve Tenjin's ATT/data fields and tracking manifest together before further attribution activation. Then implement/test the crash reporting lifecycle and accurate notice, repair the deletion routes/barrier and retention promises, and reconcile remaining public copy/store answers. Existing public statements can be corrected without pretending source-only fixes have reached installed builds. Any substantive new processing or gate change needs the coordinated version/release decision in the app skill; this audit intentionally makes none.

No simulator runtime/device was created or downloaded. No production data was queried, erased, submitted, or modified. No test run or packet capture is represented as completed; the evidence above is code, local bundled SDK inspection, and primary documentation, with specific reproduction work called out where needed.
