## Highest priorities

### 1. AudioChoices age protection exists only on initial prompt, not collection

Verified code: `shared/src/commonMain/kotlin/com/audiobookchoices/shared/persistence/UserPrefs.kt:725` computes `analyticsEnabled` solely from region + stored choice. `analytics/AnalyticsRegion.kt:160` accepts any stored true, and defaults on outside affirmative-choice regions. `ui/App.kt:1271` checks curation age >=16 only when showing the first analytics consent page. `ui/SettingsScreen.kt:1914` offers `AnalyticsRow` without an age check; its switch at 1926 calls `setAnalyticsEnabled(..., true)` directly. No age parameter or check exists in that setter (`analytics/MilestoneSync.kt:103`). Therefore under16 users in consent regions can turn it on from Settings, and a stored true continues after a downward age update. `ui/App.kt:992` enables the SDK whenever the region/choice property is true.

Website promise: `src/content/legal/audio-book-choices-privacy-policy.md:253` says measurement does not run under16 in places where consent is required. That promise is stronger than code. Correct collection behavior, not just the disclosure.

Bounded fix proposal: centralize a read-only effective analytics permission taking region, current curation age, known platform band and independently stored purpose choices; use it at every SDK initialization/resume/background/startup path, milestone ledger write/send, settings toggle and age change. In consent regions deny if age unknown or <16 even with a historical true. Disable collection immediately on age lowering; require a fresh purpose-specific opt-in after becoming eligible rather than silently resurrecting a stored yes. Refusal should remain refusal. Settings should explain unavailability and cannot set true for ineligible age. Focused tests: 15+Settings enable; consented16->15; confirmed under13; null age; restore/background; existing yes on region change; aging eligible again; no SDK enable/ledger writes/callables until effective permission.

### 2. AudioChoices admits known under13 users but claims no knowingly collected personal information

Website privacy lines441,485 say no personal information knowingly collected from under13. Line445 says a platform under13 band is accepted, with fewer stories rather than blocking use. Line453 admits Analytics is on irrespective of age outside the consent regions. Code confirms default-on and age-free analytics permission above. Anonymous Firebase UID is personal data (policy itself acknowledges at line42), Google app instance ID is a persistent identifier, and AuthGateway creates a UID for callable/RevenueCat use. Leaving age solely on the device does not remove that app's knowledge of it; absence of a name is not anonymity.

COPPA assessment is a real issue, not a finding that every operational identifier violates COPPA: FTC says general-audience actual knowledge matters, persistent identifiers count, and an internal-operations exception exists only within its conditions. Google Ads conversion measurement and normal operation must be assessed separately; calling both internal analytics is not sufficient. [FTC current FAQ](https://www.ftc.gov/business-guidance/resources/complying-coppa-frequently-asked-questions).

Bounded remedy: at minimum disable third-party advertising measurement for a known under13 band globally before SDK collection starts; do not allow Settings to override it. For backend identity, purchases/ratings and first-party milestones choose a reviewed lawful child-operational pathway meeting the applicable exception, a verified-parent pathway, or an under13 service block before nonessential collection. Keep older users' offline content accessible while stopping cloud operations if age becomes under13. Map startup ordering because the auth identifier may be minted before the onboarding age answer. Do not claim COPPA solved by only changing prose or withholding the age from the server.

### 3. AudioChoices one consent bundles two independent purposes

`ui/AnalyticsConsentScreen.kt:168` asks one yes for story engagement aggregation AND Google advertising measurement; `analytics/MilestoneSync.kt:103` controls both through one stored choice. The public privacy policy expressly justifies the single switch (sections6,9,10). These are different purposes and recipients, so consent granularity needs correcting; offer independent optional choices, separately recorded/withdrawable. Keep product access identical for refusals. [EDPB consent guidelines paragraphs55–61](https://www.edpb.europa.eu/sites/default/files/files/file1/edpb_guidelines_202005_consent_en.pdf). Consent-based information-society processing for children must meet GDPR Article8; local device permission or terms acceptance is not a substitute.

### 4. AudioChoices no-IDFA explanation falsely equates ATT with advertising-ID access

Website privacy line249: prompt exists to read advertising identifier, so SDK without IDFA means no ATT and no cross-app following. Apple explicitly defines tracking also as cross-company data linking for advertising measurement, whether or not IDFA is read. There are legitimate nontracking aggregated attribution routes, so this is not proof current setup tracks. Audit actual Google Ads link, sharing, audiences, Google signals, identifiers/install referrer, conversion settings and provider use. Remove the faulty causal sentence; state absence of IDFA separately, and describe ATT outcome only after current configuration is evidenced. [Apple tracking definition and SDK responsibility](https://developer.apple.com/app-store/user-privacy-and-data-use/), [Apple privacy preserving attribution](https://developer.apple.com/app-store/ad-attribution/).
