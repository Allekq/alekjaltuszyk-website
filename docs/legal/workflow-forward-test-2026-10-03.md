# Legal workflow forward test

Date: 2026-10-03. Read-only procedural test of the instructions currently on disk. No app, SDK, console, legal version, deployment or store state changed. No findings from the earlier product audit are used as scenario facts.

Read: website `skills/legal-update-sync/CHANGE-REVIEW.md`; OverLit `.agents/skills/legal-update-sync/SKILL.md`; their linked legal checklists and relevant website/root routing instructions.

## Fresh scenario and expected receipt

Request: ship a build adding an optional attribution SDK and changing a local export cache. Supplied consent evidence: the UMP form completed and `canRequestAds` is true. No provider, payload, cache schema, release artifact, affirmative purpose/vendor choices, dashboard settings or test traces are supplied.

This disposition is an evidence gap, not a conclusion that every attribution SDK is unlawful. A separate release that keeps attribution genuinely inactive is possible only if the requested scope permits it and initialization/automatic collection are also proven inactive; it is not an assumed workaround.

## Does the workflow lead to useful evidence?

**Yes, for the essential scenario.** The new app section at `SKILL.md:29-44` directly routes the reader to the shared review before implementation and at completion. The shared reference explicitly includes dependency/startup changes and local export/backup/retention (`CHANGE-REVIEW.md:9-19`), separates ad eligibility from optional-purpose consent (`:43-49`), asks for actual configuration and data lifecycle evidence, and provides a compact receipt instead of a generic compliance declaration. The app's marketing section specifically asks for automatic event collection, identifiers and current provider documentation. Together, these requirements cause a reader to examine SDK defaults rather than only app-authored event calls, and to review the cache without inventing a network flow.

**The legal/platform/implementation distinction is usable.** The receipt places statutory lawful basis/device access alongside, but separately from, actual SDK behavior and store/OS controls. Apple ATT and store declarations are platform checks; a UMP flag is implementation evidence; neither replaces a statutory purpose/basis assessment. The reference disclaims certification and requires recording unresolved legal judgments. I would label those evidence classes explicitly in the completed receipt, as above.

**No extra deployment permission follows from the review.** Both files expressly say the review itself does not authorize publishing/submission. In the hypothetical, “ship a build” supplies release intent, but does not prove the technical/legal prerequisites or authorize unspecified additional sharing. The appropriate path is to complete already-authorized work, prepare the concrete release and report unresolved dependencies. No repeated “may I audit/read/edit locally?” questions are required. The app skill's exact-sharing approval instruction is relevant only where the specific recipient/payload or extra automatic tracking remains outside the user's established authorization; it should not cause re-approval of an already specified implementation.

## Residual instruction problems encountered in this forward test

1. **The required app checklist still points to a forbidden version edit.** `.agents/skills/legal-update-sync/CHECKLIST.md:48-49,82` directs changing `PlayableLegalDocumentCatalog.current` versions, while canonical `SKILL.md` says those literals no longer exist and to edit `LegalAgePolicyV1` instead. Following the main skill resolves the ambiguity, but following its required checklist literally leads to the wrong place.
2. **Blanket tracker update/bump instructions still compete with the reasoned no-change outcome.** The new reference says an SDK is a review trigger, not proof of needed wording changes. The app marketing checklist at `:134` and main marketing section broadly require a changed version/update. The fresh scenario probably involves a substantive new recipient, but a genuinely already-disclosed provider integration should still be allowed the evidence-based no-change result the new reference promises. A reader currently has to reconcile general versus specific wording.
3. **The linked checklist still encourages an anonymity shortcut.** App checklist `:111` says to confirm the identity “is still anonymous” by checking absence of email/sign-in/linking. The new reference explicitly says absence of names does not establish anonymity and treats pseudonymous IDs as potentially personal data. This is an instruction-level contradiction visible without testing app behavior.
4. **The “pause and flag” reminder is weaker than the new continuation rule.** Both checklists retain wording to pause if disclosure updates are deliberately omitted. The shared reference instead directs continued authorized local remediation while identifying an affected release blocker. It does not require stopping unrelated work or asking an owner to waive obligations; a literal reader of the older reminder could still create an avoidable permission loop.
5. **Some app-specific legal pronouncements are framed too categorically to substitute for the shared evidence review.** For example, the main skill ties a role label directly to a US-law sale conclusion and describes the mere absence of an app-level `ATTrackingManager` call as sufficient to decide store correctness. A forward reviewer should treat such passages as leads to the current primary authority and actual SDK behavior, not statutory/platform/implementation equivalence. This test makes no new product-compliance finding from them.

Overall: **passes the central forward scenario with residual linked-checklist consistency issues.** The new reference would prevent approving attribution merely because UMP completed, and would require review of both automatic SDK behavior and local cache changes. It leads to a concrete evidence receipt and a scoped release disposition without authorizing deployment or demanding repetitive confirmations. The remaining conflicts are in the surrounding instructions a diligent reader is told to follow, not in the core receipt's decision structure.

## Corrections after the forward test

The parent audit corrected the residual issues above after this review: the OverLit
checklist and AdMob playbook now point to LegalAgePolicyV1; SDK additions require
an evidence-based review and substantive-only version decision; UID terminology is
pseudonymous; the app-level absence of an ATT call and a provider role label are no
longer treated as conclusive legal classifications; release blockers do not require
stopping unrelated authorized remediation. The analogous website and Take Me Somewhere
checklist reminders were also aligned. These corrections were checked on disk; the
independent scenario was not rerun after the edits.
